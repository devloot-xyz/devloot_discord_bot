# Local Discord account linking (P02)

This pilot is limited to guild `1494925337811751002` and application `1494937185101545472`. The bot uses `CORE_API_URL` to call the integrated Core server, while `CORE_WEB_URL` is the origin of the link-completion page. For the local worktrees, use Core at `http://localhost:3012` and the integrated web client at `http://localhost:5174`. Keep the existing Core container on port 3000 separate.

Apply the Core migration `20260923230000_discord_link_requests` to the isolated local database and run the integrated Core API. Configure the ignored `server/.env` with `DISCORD_SERVICE_KEY`, `DISCORD_PILOT_CLIENT_ID`, `DISCORD_PILOT_GUILD_ID`, `DISCORD_OAUTH_CLIENT_SECRET`, `DISCORD_OAUTH_REDIRECT_URI`, `API_BASE_URL`, `CLIENT_URL`, the community session secret, and GitHub OAuth credentials. The matching `DISCORD_SERVICE_KEY` belongs in this bot's ignored `.env`. The integrated client needs `VITE_API_URL` and its normal Web3Auth client ID. Never commit these files.

Register exactly `http://localhost:3012/api/discord/oauth/callback` in the development Discord application's OAuth2 redirects. The Discord grant requests only `identify`. GitHub community sign-in also needs its OAuth application to accept `http://localhost:3012/api/github/callback`. Use the same `localhost` hostname throughout browser-facing URLs so its local community cookie reaches Core after the Discord redirect.

Deploy guild commands with `npm run commands:deploy:test` and start the bot. `/connect` produces a private, ten-minute URL bound to the interaction user's Discord ID and the pilot guild. The user signs into the existing DevLoot community account, confirms the account shown on the page, and authorizes Discord. Core checks the OAuth `identify` result against the original Discord actor and atomically consumes the link request. A forwarded URL cannot link a different Discord account. Conflicts require the account holder to unlink their current association or request moderator recovery; accounts are never merged by name. No first-link reward is issued in P02.

Bot-to-Core requests use a 32-byte shared key encoded as base64. The bot signs a JWT with a 30-second lifetime, fixed issuer, audience, application subject, guild, Discord actor, and random `jti`. Core accepts at most 60 seconds and stores each `jti` once; replay, wrong audience, wrong guild, and expired assertions fail. Core prunes expired nonces and requests. The bot never sends a Core user ID as the principal. To rotate the key, stop the bot, generate a new 32-byte key, update the ignored environment files on both processes, restart Core, then restart the bot. Existing in-flight assertions become invalid. Treat a key leak as a reason to rotate before further testing.

`GET /api/discord/actor` resolves a signed Discord actor to a minimal Core identity only after that user's Discord ID has an OAuth verification timestamp. Legacy `User.discordId` values have no timestamp and remain unauthorized until the same user proves the ID through this flow. Browser endpoints require the community cookie and origin/request protection. `GET /api/discord/link` shows the current user's association and verification state, and `DELETE /api/discord/link` removes both. Unlink immediately makes actor resolution return no user and queues removal of configured managed tier roles for the old Discord ID. The Core worker must be running with its Discord guild and bot token configured to process that queue. No managed tier roles are configured in this local pilot yet.
